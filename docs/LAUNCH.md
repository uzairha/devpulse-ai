# Launch Checklist

A single sequenced list for taking DevPulse AI from "code complete" to "running
in production." The AWS mechanics live in [aws-deployment.md](aws-deployment.md);
this document is the order to do things in and the checks around them.

> **Nothing here has been executed.** Per the standing no-provisioning policy,
> no AWS resources exist and `AWS_DEPLOY_ENABLED` is unset, so the deploy
> pipeline is inert. This is the runbook for if and when that changes.

---

## 1. Pre-launch verification (local, free)

- [ ] `docker compose up -d` — Postgres + Redis healthy
- [ ] Server: `npm run lint` clean, `npm test` green (test DB migrated first — see README)
- [ ] Client: `npm run lint` clean, `npm test` green, `npm run build` succeeds
- [ ] `docker compose --profile full up --build` — all six services start; app reachable at `http://localhost:8080`
- [ ] Manual smoke (see §5) against the `full` profile
- [ ] `git status` clean, on `main`, pushed; CI green on the head commit
- [ ] Terraform: `terraform fmt -check -recursive` and `terraform validate` clean

## 2. One-time AWS bootstrap

Follow [aws-deployment.md § "Standing it up"](aws-deployment.md#standing-it-up):

- [ ] AWS account with billing alerts configured; `aws` CLI authenticated
- [ ] `terraform.tfvars` filled in (region, project name, the two user-supplied secrets)
- [ ] `terraform apply -target` the ECR repositories, then push a `bootstrap` image to each
- [ ] `terraform apply` the rest (VPC, ALB, ECS services, RDS, ElastiCache, S3, Secrets Manager)
- [ ] Run the initial `prisma migrate deploy` as a one-off Fargate task
- [ ] Confirm the ALB DNS serves the app and `/api/health` returns 200

## 3. Secrets (Secrets Manager, never in the repo)

- [ ] `JWT_SECRET` — generated by Terraform
- [ ] `DATABASE_URL`, `REDIS_URL` — assembled by Terraform from RDS/ElastiCache outputs
- [ ] `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET` — from a **production** GitHub OAuth app whose callback is `https://<domain>/api/auth/github/callback`
- [ ] `GITHUB_WEBHOOK_SECRET` — matches what repos register; `WEBHOOK_BASE_URL` set to the public HTTPS origin
- [ ] `OPENAI_API_KEY` — a key with a spend cap set

## 4. Wire up and run the deploy pipeline

Per [aws-deployment.md § "Wire up the deploy pipeline"](aws-deployment.md#4-wire-up-the-deploy-pipeline):

- [ ] Create the GitHub OIDC role that trusts this repo; set `AWS_DEPLOY_ROLE_ARN`, `AWS_REGION`, the `ECR_*` / `ECS_*` / subnet / security-group repo variables
- [ ] Set `AWS_DEPLOY_ENABLED = true` (the master switch — until then the job is skipped)
- [ ] Push to `main` (or run the workflow manually). The pipeline: builds + pushes the backend and frontend images under `sha-<commit>`, runs `prisma migrate deploy` as a one-off task, then updates the backend → frontend → worker services and waits for each to stabilise. A failed migration stops the deploy before any service changes.

## 5. Post-deploy smoke test

Against the production URL:

- [ ] `GET /api/health` → 200; `GET /api/health/ready` → 200 (DB + Redis reachable)
- [ ] Register a throwaway account, then log out and back in
- [ ] Sign in with GitHub; confirm the OAuth round-trip and token land you on the dashboard
- [ ] Connect a repository → a sync job runs → PR/commit data appears in analytics
- [ ] Generate a weekly report; open the AI chat and ask one question
- [ ] Toggle dark mode; confirm it persists across a reload
- [ ] Push a commit to the connected repo → webhook fires → a sync notification appears
- [ ] CloudWatch: no error-level logs from the smoke; alarms (if enabled) not firing

## 6. Rollback

- **App regression:** re-run the deploy workflow with `workflow_dispatch` and the previous good `image_tag` (`sha-<older-commit>`). Services roll to that task definition; no rebuild needed.
- **Bad migration:** `migrate deploy` is forward-only. Roll back with a new migration that reverses the change, deployed the normal way. Restore from the RDS automated snapshot only if data is corrupted.
- **Full stop:** scale the ECS services to 0 desired count; the ALB returns 503 while you investigate.

## 7. Known gaps at launch

Tracked in [aws-deployment.md § "Known gaps"](aws-deployment.md#known-gaps) and the development log:

- No custom domain / TLS wired by default — add per aws-deployment.md § "Adding TLS" (until then the ALB is HTTP only)
- CloudWatch alarms are off by default (`enable_alarms = false`)
- Analytics cache invalidation uses `redis.keys()` — fine at this scale, not for a large keyspace
- Webhook delivery can't be verified without a public URL, so it's untested in CI
- No end-to-end/browser test layer; `Header` sub-components and a few services are covered only through the route suites
