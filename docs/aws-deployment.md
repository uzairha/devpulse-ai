# AWS Deployment

How the DevPulse AWS deployment is put together, what it would cost, and the
exact sequence to stand it up — for whenever someone decides to.

> **Nothing here has been applied.** No AWS resources have been provisioned and
> none are being billed. There is no Terraform state, no remote backend, no
> stored AWS credentials, and the deploy workflow is gated on a repository
> variable that does not exist. See [Deployment status](../README.md#deployment-status)
> in the root README for the standing no-provisioning policy — this document
> describes a deployment, it does not perform one.

---

## Architecture

```
                        Internet
                            │
                    ┌───────▼────────┐
                    │      ALB       │  :80 (→ :443 redirect once TLS is on)
                    └───┬────────┬───┘
              /api/*    │        │    everything else
                    ┌───▼───┐ ┌──▼─────┐  ┌──────────┐
                    │backend│ │frontend│  │  worker  │  ECS Fargate (ARM64)
                    │  API  │ │ nginx  │  │  BullMQ  │  no ALB route
                    └───┬───┘ └────────┘  └────┬─────┘
                        │                      │
              ┌─────────┴──────────┬───────────┘
        ┌─────▼─────┐      ┌───────▼────────┐      ┌──────────────┐
        │    RDS    │      │  ElastiCache   │      │      S3      │
        │ Postgres  │      │ Redis AUTH+TLS │      │   uploads/   │
        └───────────┘      └────────────────┘      └──────────────┘
             private subnets, no internet route        via task role
```

**Three services, two images.** The worker runs the backend image with its
command overridden to `node src/worker.js` — identical dependency tree, Prisma
client and config module, so a separate image would duplicate every layer for
nothing. This mirrors `docker-compose.yml`'s `full` profile exactly.

**One ALB, path-routed.** `/api/*` goes to the backend target group, everything
else to nginx. Frontend and API therefore share one public origin, which is why
there is no production CORS configuration to manage and why the client's axios
base URL is the relative `/api` — nothing is baked into the bundle at build
time, so the same frontend image works at any hostname.

**The worker is not behind the ALB.** Nothing addresses it over HTTP, so it has
no target group and no container health check.

### Files

| File | Contains |
|---|---|
| `versions.tf` | Terraform and provider version constraints |
| `providers.tf` | AWS provider, default tags |
| `variables.tf` | Every input variable, grouped by concern |
| `networking.tf` | VPC, subnets, IGW, route tables, optional NAT |
| `security-groups.tf` | The ALB → ECS → RDS/Redis chain |
| `ecr.tf` | Image repositories and lifecycle policies |
| `iam.tf` | ECS execution and task roles |
| `load-balancer.tf` | ALB, target groups, listeners |
| `ecs.tf` | Cluster, task definitions, services |
| `rds.tf` / `redis.tf` / `s3.tf` | Data stores |
| `secrets.tf` | Secrets Manager |
| `cloudwatch.tf` | Log groups and alarms |
| `outputs.tf` | Values needed after apply |

## Security posture

What the configuration does, and why — the parts worth knowing before changing
any of it.

### Network

Nothing but the ALB is reachable from the internet. RDS and ElastiCache accept
traffic **only from the ECS security group**, never from a CIDR block, so no
subnet misconfiguration alone can expose them. Both stay in private subnets
regardless of the NAT toggle — a database never needs a route out.

`enable_nat_gateway = false` (the example default) moves the *ECS tasks* to the
public subnets to avoid the NAT Gateway's fixed cost. A public IP is not an open
port: inbound is still restricted to the ALB security group. It is a cost
tradeoff, not a security one — but `true` is the posture to use for anything
long-lived.

### Identity

Two role types, kept separate on purpose:

- **Execution role** — used by the ECS agent *before* the container starts, to
  pull the image, open the log stream and resolve secrets. Application code
  never assumes it.
- **Task role** — assumed by the application itself for its own AWS calls.

So a compromised application process cannot pull other images or read arbitrary
secrets through its own credentials. Secrets Manager access is scoped to the
five exact secret ARNs; S3 access is scoped to one bucket's `uploads/` prefix.
No `*` resources anywhere. The frontend has **no task role at all** — nginx
serves static files and calls no AWS API, so there is nothing to grant it.

### Secrets

Five secrets. Three (`DATABASE_URL`, `REDIS_URL`, `JWT_SECRET`) are generated by
Terraform — there is no human-typed value to leak, only one the configuration
invents and immediately stores. Two come from real external accounts (OpenAI, a
GitHub OAuth App), supplied through `terraform.tfvars` and marked `sensitive` so
no plan or apply prints them.

`ecs.tf` reads the secret ARNs directly, so the value stored and the value
injected into the container can never drift apart.

> **Terraform state holds all of these in plaintext.** That is inherent to
> Terraform, not a flaw here — the database password, the Redis AUTH token and
> the JWT signing key all appear in state as literal strings. `.gitignore`
> covers `*.tfstate*`, `terraform.tfvars` and `*.tfplan`, and state is local
> with no remote backend. If you ever move state to S3, that bucket needs
> encryption, versioning and blocked public access before anything is written
> to it.

### Transport

RDS storage is encrypted; ElastiCache is encrypted at rest **and** in transit,
with an AUTH token — so landing inside the security group is not by itself
enough to talk to Redis. That is also why `REDIS_URL` uses the `rediss://`
scheme: ElastiCache requires TLS whenever an auth token is set.

The ALB serves plain HTTP until `certificate_arn` is set. Once it is, the
`:80` listener **stops serving the application entirely and only issues a 301
to HTTPS** — every API request carries an `Authorization: Bearer` token, and
leaving a plaintext route open would just be an alternate way to hand those
tokens to anyone on the path.

### Images

ECR repositories are **immutable**: a pushed tag can never be overwritten, so
the image a running service points at cannot be silently swapped, and a tag
recorded in a task definition provably refers to one specific build forever.
`scan_on_push` is on for both.

This is also why nothing pushes `:latest` — under immutability a moving tag can
only be written once, so the second deploy would fail at the push step. Every
deploy tags `sha-<commit>` and renders that exact tag into the task definition.
The one exception is the hand-pushed `bootstrap` tag, which exists only because
a task definition must name *some* image on the very first apply.

### Application

Already handled in the app itself, not in Terraform, but relevant to the
deployment:

- `config/index.js` **fails fast** rather than booting production with a
  publicly-known JWT secret or no database — a crash-looping task is far
  cheaper than one serving forgeable tokens.
- `TRUST_PROXY_HOPS=1` behind the ALB, so rate limiting keys on the real client
  IP from `X-Forwarded-For` and not on the load balancer's own address.
- `RUN_WORKERS_IN_API=false` in production, so the API does not also consume
  jobs — two consumers would double-process every sync.
- `/api/health/ready` reports booleans only, never the driver error, host or
  version, since it is reachable through the load balancer.
- The error handler suppresses stack traces and messages on 500s in production.
- Both containers run as a non-root user; the backend uses `tini` as PID 1 so
  ECS's `SIGTERM` on task drain is actually forwarded.

## Cost

Rough `us-east-1` figures for the example defaults, for a deployment left
running continuously. **Applying this configuration costs real money** — there
is no free tier that covers all of it.

| Component | Configuration | Approx. monthly |
|---|---|---|
| ECS Fargate | 3 × 0.25 vCPU / 0.5 GB, ARM64 | ~$22 |
| ALB | 1, low traffic | ~$18 |
| RDS | `db.t4g.micro`, 20 GB gp3, single-AZ | ~$14 |
| ElastiCache | `cache.t4g.micro`, 1 node | ~$12 |
| NAT Gateway | **disabled** in the example tfvars | $0 (~$32 if enabled) |
| Secrets Manager | 5 secrets | ~$2 |
| CloudWatch Logs | 14-day retention, low volume | ~$1 |
| S3 / ECR | Minimal | ~$1 |

The cost-shaped defaults are all deliberate and all documented at their variable:
ARM64/Graviton throughout, NAT off, no Multi-AZ, no automated backups, alarms
off (an alarm with no SNS subscriber is silent and still bills per alarm-month),
Container Insights off, and `secrets_recovery_window_days = 0` so a destroy
leaves nothing behind still being billed.

**The single largest saving is `enable_nat_gateway = false`.** The single
largest remaining cost is the ALB, which cannot be avoided while there is a
load balancer at all.

## Standing it up

Only for someone who has decided to spend the money above. Steps 1–3 are
one-time.

### Prerequisites

- Terraform ≥ 1.6 (or OpenTofu — this configuration is validated with both)
- AWS CLI v2, authenticated to an account you are willing to bill
- Docker with buildx (the images are ARM64)
- A GitHub OAuth App and an OpenAI API key

### 1. Variables

```bash
cd infrastructure/aws/terraform
cp terraform.tfvars.example terraform.tfvars
```

Fill in the four credential values at the bottom. Everything above them is
sizing, naming and cost choices, already set to the cheapest practical values.
`terraform.tfvars` is gitignored.

### 2. Create the repositories, then bootstrap an image

The task definitions must name an image that exists, so ECR comes first:

```bash
terraform init
terraform apply -target=aws_ecr_repository.backend -target=aws_ecr_repository.frontend
```

Push one image to each under the `bootstrap` tag:

```bash
BACKEND_URL=$(terraform output -raw ecr_backend_repository_url)
FRONTEND_URL=$(terraform output -raw ecr_frontend_repository_url)

# The registry host is the part of the repository URL before the first slash.
aws ecr get-login-password --region "$(aws configure get region)" \
  | docker login --username AWS --password-stdin "${BACKEND_URL%%/*}"

docker buildx build --platform linux/arm64 -t "$BACKEND_URL:bootstrap"  --push ../../../server
docker buildx build --platform linux/arm64 -t "$FRONTEND_URL:bootstrap" --push ../../../client
```

`--platform linux/arm64` is not optional: the task definitions declare an ARM64
runtime platform, and an x86 image will fail to start on it.

### 3. Apply the rest

```bash
terraform apply
```

Then run the migrations once by hand, because no deploy has run yet to do it
(see [Database migrations](#database-migrations)). The task definition family
and the service share a name in `ecs.tf`, which is why one output supplies both
here:

```bash
aws ecs run-task \
  --cluster "$(terraform output -raw ecs_cluster_name)" \
  --task-definition "$(terraform output -raw ecs_backend_service_name)" \
  --launch-type FARGATE \
  --network-configuration "awsvpcConfiguration={subnets=[$(terraform output -json ecs_subnet_ids | jq -r 'join(",")')],securityGroups=[$(terraform output -raw ecs_security_group_id)],assignPublicIp=$(terraform output -raw ecs_assign_public_ip)}" \
  --overrides '{"containerOverrides":[{"name":"backend","command":["npx","prisma","migrate","deploy"]}]}'
```

The application should now answer at `terraform output -raw application_url`.

### 4. Wire up the deploy pipeline

`.github/workflows/deploy-aws.yml` is inert until two independent things are
true, and it stores no AWS credentials at all.

**OIDC role.** Create an IAM role that trusts GitHub's OIDC provider, with its
trust policy scoped to *this repository* (`repo:<owner>/<repo>:*`), not to `*`.
It needs permission to push to the two ECR repositories, register task
definitions, update the three services, run the migration task, and `iam:PassRole`
for the execution and task roles. There are no long-lived access keys anywhere
in this design and there should never be.

**Repository variables** (Settings → Secrets and variables → Actions →
Variables). All are non-secret identifiers:

| Variable | Value |
|---|---|
| `AWS_DEPLOY_ENABLED` | `true` — the master switch |
| `AWS_DEPLOY_ROLE_ARN` | The OIDC role above |
| `AWS_REGION` | e.g. `us-east-1` |
| `ECR_BACKEND_REPOSITORY_URL` | `terraform output -raw ecr_backend_repository_url` |
| `ECR_FRONTEND_REPOSITORY_URL` | `terraform output -raw ecr_frontend_repository_url` |
| `ECS_CLUSTER_NAME` | `terraform output -raw ecs_cluster_name` |
| `ECS_BACKEND_SERVICE` | `terraform output -raw ecs_backend_service_name` |
| `ECS_FRONTEND_SERVICE` | `terraform output -raw ecs_frontend_service_name` |
| `ECS_WORKER_SERVICE` | `terraform output -raw ecs_worker_service_name` |
| `ECS_SUBNET_IDS` | `terraform output -json ecs_subnet_ids \| jq -r 'join(",")'` |
| `ECS_SECURITY_GROUP_ID` | `terraform output -raw ecs_security_group_id` |
| `ECS_ASSIGN_PUBLIC_IP` | `terraform output -raw ecs_assign_public_ip` |
| `ALB_DNS_NAME` | `terraform output -raw alb_dns_name` |

Until `AWS_DEPLOY_ENABLED` is exactly `true`, the job shows as skipped and
nothing after the gate executes. Setting it is the deliberate act that ends the
no-provisioning policy — which is why this document tells you how, and does not
tell you to.

## The deploy pipeline

**CI** (`ci.yml`) runs on every push and PR and touches AWS in no way — no
credentials are read or needed, so it keeps working for anyone who clones this
repository. Four parallel jobs: server lint + the 73-test integration suite
against Postgres and Redis service containers; client lint + tests + a
production build; both Docker images built and discarded; and
`terraform fmt`/`validate` with `-backend=false`.

**Deploy** (`deploy-aws.yml`) fires after CI succeeds on `main`, or manually.
Order matters:

1. Assume the OIDC role, log in to ECR.
2. Build and push both images, tagged `sha-<commit>` — one immutable tag each.
3. Render the new backend image into the current task definition and register
   that revision.
4. **Run migrations** as a one-off Fargate task from that revision.
5. Update the backend service, then frontend, then worker — each waited to
   steady state.
6. `curl` `/api/health` and `/healthz` through the ALB, so the pipeline
   confirms the application actually answers rather than only that ECS thinks
   the tasks are healthy.

### Database migrations

Step 4 runs the **new** image with its command overridden to
`npx prisma migrate deploy`, before any service is updated. If it ran after,
new code would serve requests against a schema missing its columns, and every
request in that window would fail. If it fails, the job stops there and the
services keep running the previous image rather than half-deploying against a
half-migrated database.

This works because `prisma` is a regular dependency rather than a
devDependency, so both the CLI and `prisma/schema.prisma` survive
`npm ci --omit=dev` into the production image. `migrate deploy` only applies
pending migrations — it never generates, resets or prompts — and it takes an
advisory lock, so a concurrent deploy waits instead of racing.

> Locally, remember that `node --watch` does **not** watch `node_modules/`, so
> the dev server must be killed and restarted after any `prisma migrate` — a
> `src/` edit restarting it is not enough to pick up the regenerated client.

### The npm version pin

Both Dockerfiles install `npm@11.12.1` before `npm ci`. `node:22-alpine` bundles
npm 10, whose resolver treats this lockfile's `eslint@^9` / `@eslint/js@^10`
optional peer conflict as fatal — even under `--omit=dev`, where neither package
is installed at all. The pin is the version the lockfile was authored with. It
can go away whenever that peer range is reconciled.

## Adding TLS

1. Request an ACM certificate in the same region for your domain, and validate
   it (DNS validation is simplest).
2. Point the domain at the ALB — a Route 53 ALIAS using `alb_dns_name` and
   `alb_zone_id`, or a CNAME anywhere else.
3. Set both `certificate_arn` and `app_domain` in `terraform.tfvars`, and apply.

That one apply changes three things together: an HTTPS listener appears on
`:443` with a TLS 1.3 policy, the `:80` listener drops the application and
becomes a 301 redirect, and `CLIENT_URL` / `GITHUB_CALLBACK_URL` /
`WEBHOOK_BASE_URL` switch to the `https://` scheme. Update the GitHub OAuth
App's callback URL to match, or login will break — GitHub matches it exactly.

The scheme follows the *certificate*, not the domain: setting `app_domain`
alone leaves the app on HTTP and the environment variables honestly say so.

## Adding alarms

Alarms are off by default because one with no subscriber is silent and still
bills per alarm-month. Create an SNS topic, subscribe an email or Slack webhook,
confirm the subscription, then:

```hcl
enable_alarms = true
alarm_actions = ["arn:aws:sns:us-east-1:123456789012:devpulse-alerts"]
```

That creates seven: unhealthy ALB targets (backend and frontend), elevated 5xx,
sustained high CPU on backend, worker, RDS and ElastiCache.

## Remote state

State is local, which is right for a configuration nobody has deployed from.
A team deployment would move it to S3 — the bucket must exist first, which is
why this configuration does not create it:

```hcl
# versions.tf
terraform {
  backend "s3" {
    bucket       = "devpulse-terraform-state"
    key          = "production/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true   # S3-native locking, Terraform 1.10+; on older
                          # versions use dynamodb_table instead
  }
}
```

Adding this also means raising `required_version` in `versions.tf`, which
currently allows 1.6.

That bucket holds every secret in plaintext (see [Secrets](#secrets)) — give it
versioning, SSE and a public access block before writing anything to it.

## Tearing it down

```bash
terraform destroy
```

The defaults are set so this leaves nothing billing: `db_deletion_protection`
and `db_multi_az` off, `db_skip_final_snapshot` on, `s3_force_destroy` on, and
`secrets_recovery_window_days = 0` so secrets are deleted immediately rather
than lingering for up to 30 days.

Two things `destroy` will not clean up:

- **ECR images.** The repositories are immutable and hold pushed images;
  delete them (or the repositories) explicitly.
- **CloudWatch log groups** that have received data may need removing by hand.

Raise every one of those settings before pointing this at anything holding data
you would miss — they are tuned for a demo that is meant to be disposable.

## Known gaps

Honest list of what this deployment does *not* do, all deliberate:

- **No autoscaling.** Fixed `desired_count` per service. Fine at demo scale;
  a real deployment wants an ECS service autoscaling target.
- **No blue/green.** `update-service` does a rolling replacement. CodeDeploy
  with an ECS blue/green deployment group would give real rollback.
- **No WAF** in front of the ALB.
- **No VPC endpoints.** With NAT disabled, ECR pulls and CloudWatch writes go
  out over the internet gateway rather than staying on the AWS network.
- **Backups are off** (`db_backup_retention_days = 0`), because the seed data
  is trivially reproducible with `npm run seed`. Turn this on before real data
  exists.
- **Webhook delivery health is unverifiable locally** — it needs a public URL,
  which is exactly what this deployment would provide.
